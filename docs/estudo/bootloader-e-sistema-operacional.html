Escopo: primeiro o mínimo entregável, com terminal serial em um computador de apoio com Linux. Este documento explica o comportamento que vamos implementar; não afirma que o firmware, o SO ou a emulação já estão prontos. Os textos para a proposta são sugestões para sua revisão, não respostas já aprovadas por você.

1. Três programas, três responsabilidades

Bootloader, sistema operacional e jogo são software: sequências de instruções que a mesma CPU Z80 executa em momentos diferentes. Não são três chips adicionais.

1. BootloaderComeça após o reset, prepara o necessário e carrega o SO.
2. Sistema operacionalAtende comandos e carrega/inicia a aplicação.
3. AplicaçãoPrograma interativo simples em texto. Adivinhação é uma possibilidade; o aplicativo ainda será escolhido.
RESET → boot na EEPROM → SO na RAM → comando → programa na RAM
             Z80 executa todos esses códigos, um de cada vez
NomeUma explicação simplesNão confundir com
BootloaderO programa que prepara a partida e coloca o SO em execução.O circuito de reset, que apenas coloca a CPU no estado inicial.
SO mínimoNosso programa de controle: comandos, entrada/saída e carregamento de aplicações.Um Linux completo, com interface gráfica, arquivos e vários processos.
AplicaçãoO programa que será carregado e usado depois: jogo ou outro programa interativo.O SO em si. Precisamos demonstrar que o SO carrega e inicia um programa.

O professor quer acompanhar essa separação: ligar → iniciar do endereço de reset → carregar o sistema → executar um comando → carregar e executar uma aplicação. Mostrar só uma mensagem fixa na ROM não demonstra tudo isso.

2. Onde cada coisa fica no nosso computador

Usaremos exatamente o mapa já documentado no campo 4. Não há uma nova distribuição de endereços neste guia.

EndereçosMemóriaConteúdo planejado

8000h–BFFFhRAM · 16 KiBSO em execução, seus dados e buffers.

O que é a “imagem do SO”?

É a representação binária do sistema: os bytes que armazenamos na EEPROM para depois copiar para a RAM. Não é uma imagem visual e não precisa ser um arquivo de disco ou uma imagem de Linux.

Antes da cópia:
EEPROM 4000h–7FFFh → bytes guardados da imagem do SO
RAM    8000h–BFFFh → conteúdo ainda não inicializado pelo nosso código

Depois da cópia:
EEPROM 4000h–7FFFh → continua com a mesma imagem
RAM    8000h–BFFFh → recebeu uma cópia desses bytes

Depois do salto para 8000h:
Z80 passa a buscar instruções do SO na RAM.

Copiar não apaga a EEPROM. Ao desligar, a imagem continua lá; o conteúdo da RAM deixa de ser garantido. Ao ligar novamente, o boot repete a inicialização.

Um detalhe importante de construção: o SO deve ser montado para executar a partir de 8000h, embora sua imagem seja armazenada a partir de 4000h na EEPROM. O código precisa usar os endereços de execução corretos. “Montar”, aqui, significa converter Assembly em bytes com um montador.

A versão inicial pode copiar uma região fixa de 16 KiB, preenchida na construção da imagem. Isso inclui espaço para dados iniciais; áreas que precisem começar zeradas devem ser preparadas pela imagem ou pela inicialização. Não presumiremos que a RAM liga zerada.

3. Campo 5 — o bootloader, passo a passo

Quem coloca o bootloader na EEPROM?

Nós, durante o desenvolvimento, usando um gravador compatível. O computador precisa de código válido na EEPROM antes da primeira partida. O Z80 não cria o bootloader sozinho e o terminal não precisa enviar o SO a cada reset na estratégia escolhida.

O que acontece ao ligar?

  1. O hardware estabiliza: alimentação, clock e reset devem funcionar corretamente. Código não corrige uma alimentação errada.
  2. A CPU sai do reset: no Z80, a execução começa em 0000h. Nosso circuito mapeia a EEPROM nesse endereço.
  3. Começa o boot: a posição 0000h conterá o início do código, normalmente um salto para a rotina principal do boot, deixando espaço para organizar os vetores.
  4. Prepara a pilha: configura SP para uma região válida da RAM, antes de usar chamadas de subrotina ou operações que dependam da pilha.
  5. Inicializa a interface serial: prepara as rotinas de entrada e saída usadas pelo SO. A arquitetura definida usa o Arduino Uno (ATmega328P) como periférico paralelo, com 00h para dados e 01h para estado/controle; o SIO/2 é a alternativa. A sequência exata de handshake e a interface elétrica serão detalhadas no esquemático e testadas na bancada.
  6. Informa a partida: envia uma mensagem pela serial para indicar que o código inicial está executando.
  7. Carrega o SO: copia a imagem da EEPROM, iniciando em 4000h, para a RAM, iniciando em 8000h. Podemos acrescentar verificação da cópia antes de prosseguir.
  8. Transfere o controle: executa um salto para a entrada do SO em 8000h.
“Transferir o controle” não significa mover uma unidade de controle. Significa mudar o endereço de onde a CPU busca as próximas instruções. O PC passa a apontar para a entrada do sistema.

Quando o boot termina?

Quando o SO assume a execução. O boot permanece guardado na EEPROM, mas não fica rodando em paralelo ao sistema. Na versão inicial, usaremos consulta de status por software, sem habilitar interrupções até que os respectivos vetores e rotinas estejam implementados.

O que aprender nesta parte

  • Por que o código inicial precisa estar em memória não volátil e em um endereço acessível após reset.
  • Diferença entre armazenar, copiar e executar código.
  • O que significam PC, SP, inicialização e salto.
  • Por que uma mensagem serial ajuda a identificar até onde a partida chegou.

4. Campo 6 — o nosso sistema operacional mínimo

Depois que recebe o controle, o SO prepara seu estado e mostra um prompt: um texto indicando que está esperando um comando. Exemplo ilustrativo:

Hiraishin-Z80
Sistema pronto.
HIRA>

Essas mensagens são exemplos de interface, não saídas de software já funcionando.

Responsabilidades da primeira versão

  • Entrada: ler caracteres recebidos pela UART.
  • Saída: enviar caracteres e mensagens pela UART.
  • Comandos: receber uma linha, reconhecer o pedido e executar a ação.
  • Carregamento: receber um programa e armazená-lo na área de aplicação.
  • Execução: iniciar o programa carregado, com um caminho definido para retornar ao SO.
  • Serviços: oferecer rotinas que a aplicação possa chamar para entrada e saída, sem reimplementar toda a comunicação.
Comando sugeridoComportamentoO que demonstra
HELPLista os comandos disponíveis.Leitura, interpretação e resposta.
LOADRecebe um binário pela serial e valida a carga na RAM.Carregamento de programa pelo nosso código.
RUNInicia a aplicação válida em C000h.Execução de um programa separado do SO.

Os nomes são uma sugestão de interface; os comandos ainda serão implementados e testados. LOAD deve deixar a aplicação marcada como inválida até o recebimento e a verificação terminarem; RUN não deve executar uma carga incompleta.

O que não precisamos fazer inicialmente

Não precisamos de interface gráfica, disco, sistema de arquivos, instalação de pacotes, usuários, rede, memória virtual ou multitarefa. Nosso sistema pode ser um monitor de comandos com carregador e serviços simples, desenvolvido por nós para esta máquina.

Um programa por vez: quando a aplicação está em execução, o SO não fica necessariamente processando comandos em paralelo. Seu código continua na RAM e pode ser chamado por serviços; o prompt volta quando a aplicação devolve o controle.

O que aprender nesta parte

  • Diferença entre SO e aplicação.
  • Como caracteres viram uma linha de comando.
  • Por que o SO precisa conhecer o mapa de memória e a interface da UART.
  • O que significa carregar um programa separado, em vez de apenas colocar tudo em um único código fixo na ROM.

5. Como um programa sai do Linux e chega ao Z80

Arquivo binário no computador Linux
                ↓ ferramenta de envio
Terminal Linux ↔ interface serial escolhida ↔ Z80 executando o comando LOAD
                                       ↓
                              RAM C000h–EFFFh
                                       ↓ RUN
                              execução em C000h

O Linux é a máquina de desenvolvimento e o terminal. O programa precisa ser gerado para Z80: um executável nativo de Linux/Ryzen não funciona nessa CPU.

Enviar bytes não é o mesmo que executar

  1. O SO consulta a UART e recebe um byte.
  2. O Z80 escreve esse byte no endereço de destino da RAM.
  3. Repete até receber o programa completo, usando um protocolo de transferência.
  4. Verifica tamanho, destino e integridade.
  5. Somente depois, RUN inicia a execução no endereço de entrada.

O terminal e a interface serial não sabem, por si, onde começa o programa na RAM. Quem faz essa decisão e as escritas é nosso carregador, executado pelo Z80.

Regras do carregador

  • Na versão inicial, manter o destino na área de aplicação, começando em C000h.
  • Rejeitar tamanho zero, tamanho maior que 12 KiB ou qualquer transferência que ultrapasse EFFFh. A verificação deve tratar também estouro aritmético.
  • Não permitir que a carga sobrescreva o SO nem a área reservada à pilha.
  • Definir início, comprimento e verificação de integridade no protocolo; tratar erro, cancelamento e recebimento incompleto.
  • Controlar o ritmo da transmissão para evitar perda de dados na UART. A simples existência de um checksum não impede perda de bytes.
Ainda será especificado: formato exato do cabeçalho, algoritmo de verificação, controle de fluxo e ferramenta de envio. Vamos defini-los antes de implementar os dois lados. Um checksum detecta certos erros de transmissão; não é garantia de que o programa está correto ou é seguro.

Sem armazenamento adicional: o programa carregado na RAM precisa ser reenviado após desligar ou reiniciar o sistema. O SO, por outro lado, pode ser recarregado automaticamente da imagem na EEPROM.

6. Pilha, subrotinas e serviços do SO

Para que serve a pilha?

É uma área da RAM usada para guardar temporariamente informações, como o endereço para onde voltar após uma chamada. O registrador SP indica a posição corrente da pilha.

No Z80, uma chamada CALL guarda o endereço de retorno na pilha; RET o recupera. A pilha cresce para endereços menores. Nosso plano começa com SP em FFFEh, dentro da área reservada. Precisaremos dimensionar o uso para que ela não invada a aplicação.

Como o programa pode voltar ao SO?

Uma estratégia simples será o SO chamar a entrada da aplicação em C000h usando CALL. Se a aplicação preservar o estado necessário da pilha, poderá retornar usando RET. O SO então reapresenta o prompt. A convenção exata de registradores e retorno ainda será definida.

O que é uma chamada de serviço?

É uma forma combinada de a aplicação pedir uma tarefa ao SO. Por exemplo:

Aplicação: “envie este caractere”
    ↓ chama a rotina de saída do SO
SO: consulta o estado da UART e envia o caractere
    ↓ retorna
Aplicação continua

Podemos começar com serviços para enviar e ler um caractere. Consultar se há entrada disponível, sem bloquear a execução, poderá ser acrescentado para o runner, caso esse diferencial seja desenvolvido depois do mínimo. Esperar uma tecla a cada passo pararia a animação.

Esses serviços podem ser subrotinas acessíveis por uma tabela de entrada estável. Não precisam envolver interrupção nem troca de privilégio. Antes de programar a aplicação, definiremos a convenção: como passar argumentos, onde receber resultados e quais registradores são preservados. Não atribuiremos endereços arbitrários aqui.

Limite do sistema mínimo: não haverá proteção de memória impedindo uma aplicação defeituosa de sobrescrever o SO. A validação do carregador reduz erros de carga; não cria isolamento durante a execução.

7. Como vamos construir e testar por etapas

Fluxo escolhido para a primeira entrega: bootloader, SO inicial e primeira aplicação em Assembly Z80, escritos no computador Linux e convertidos em binários por um montador. O montador roda no Linux, não no Z80. C e linguagens interpretadas ficam fora desse primeiro marco.

No Linux: arquivo Assembly → montador Z80 → arquivo binário
Boot + imagem do SO → gravador externo → EEPROM (persistente)
Aplicação → envio pela serial → carregador do SO → RAM C000h
RUN → execução pelo Z80

Começaremos por comandos separados: montar o arquivo, iniciar LOAD no terminal, enviar o binário com uma ferramenta compatível com o protocolo e executar RUN. Essa ferramenta de envio é necessária, mas não precisa ser uma IDE personalizada. Botão de deploy, integração com editor e envio/execução automáticos são opcionais, não compromissos da entrega.

  1. Primeira saída: gerar uma pequena ROM que começa em 0000h e escreve uma mensagem pela UART. É um teste intermediário, não o bootloader completo.
  2. RAM: escrever e ler padrões conhecidos em endereços de teste sem destruir código ou pilha.
  3. Cópia e salto: colocar uma rotina na imagem em EEPROM, copiar para 8000h e provar que a mensagem seguinte veio de código executado na RAM.
  4. SO: implementar entrada de caracteres, linha de comando, HELP e prompt.
  5. Carga: implementar LOAD, validações e RUN. Primeiro executar um programa pequeno que imprime uma mensagem e retorna.
  6. Interação: executar uma aplicação separada simples em texto que lê uma entrada e produz uma resposta; validar o conjunto e concluir PCB, testes e entregas acadêmicas.
Depois do mínimo, somente se houver tempo: desenvolver o Hiraishin Runner com entrada não bloqueante, atualização de tela e temporização, medindo os limites do terminal serial. Vídeo dedicado, som e controle PS2 também são diferenciais opcionais, não etapas obrigatórias para concluir a entrega principal.

8. Sugestões de resposta para a proposta

Use estes textos depois de entender o caminho descrito. Assembly é o fluxo inicial escolhido; a convenção de serviços e o protocolo ainda serão especificados. O firmware será desenvolvido e testado, não apresentado como já pronto.

Campo 5 — Bootloader

O bootloader será próprio, inicialmente escrito em Assembly Z80 e gravado na EEPROM AT28C256, com entrada no endereço de reset 0000h. Ele inicializará a pilha e a interface serial, usando a arquitetura de registradores definida para o Arduino Uno/ATmega328P (00h para dados e 01h para estado/controle; SIO/2 como alternativa), copiará a imagem do sistema operacional da faixa 4000h–7FFFh da EEPROM para 8000h–BFFFh da RAM e transferirá a execução para 8000h. O código inicial permanecerá disponível na EEPROM para repetir a partida após cada reset. A temporização e os detalhes elétricos do handshake serão verificados no esquemático e na bancada.

Campo 6 — Sistema operacional

O sistema operacional será próprio e minimalista, inicialmente escrito em Assembly Z80 e executado na RAM. Oferecerá um terminal de comandos pela serial, com ajuda, carregamento e execução de programas. O carregador receberá binários do computador de apoio com Linux, verificará tamanho, faixa de destino e integridade e os armazenará na área C000h–EFFFh. O sistema também oferecerá rotinas de entrada e saída para as aplicações e um mecanismo definido de retorno ao prompt. A primeira versão executará uma aplicação por vez, sem sistema de arquivos ou multitarefa.

9. Perguntas para conferir seu entendimento

Tente responder antes de abrir a explicação. Não precisa decorar frases: procure explicar o caminho dos dados e das instruções.

1. O bootloader é um chip?

Não. É código armazenado na EEPROM e executado pela CPU Z80.

2. Como o Z80 encontra o primeiro código?

Após reset válido, começa em 0000h. Nosso mapa coloca a EEPROM nessa faixa, com instruções válidas de partida.

3. O reset carrega o SO?

Não. O reset inicia o estado da CPU. Depois disso, as instruções do bootloader fazem a cópia e o salto.

4. O que muda ao copiar o SO de 4000h para 8000h?

Os bytes da imagem passam a existir também na RAM. Só depois do salto a CPU começa a executar o sistema nesse destino; a EEPROM não é apagada.

5. O bootloader e o SO recebem o jogo pela serial?

Na estratégia inicial, o boot carrega o SO da EEPROM. O carregador do SO recebe a aplicação pela serial. São duas cargas diferentes.

6. Onde estão o SO guardado e o SO executando?

A imagem fica em 4000h–7FFFh na EEPROM. A região de execução, dados e buffers fica em 8000h–BFFFh na RAM.

7. Por que a aplicação não deve ser carregada em 8000h?

Porque sobrescreveria a área do SO. Reservamos C000h–EFFFh para a aplicação.

8. Quem recebe o byte serial e grava na RAM?

A UART recebe os sinais seriais. O Z80, executando o nosso carregador, lê os registros da UART e escreve os bytes nos endereços de RAM previstos.

9. Quem executa a aplicação: Linux ou Z80?

No protótipo físico, o Z80. Linux prepara os arquivos, envia os dados e mostra o terminal. Durante a emulação, o Z80 virtual roda dentro do computador de apoio.

10. Por que configurar SP antes de usar CALL?

Porque CALL precisa guardar o endereço de retorno na pilha. Um SP não preparado pode causar escrita em uma região indevida e impedir o retorno correto.

11. Mostrar um prompt já cumpre tudo?

Não. Precisamos demonstrar comandos e, principalmente, que nosso código carrega e inicia um programa separado, com entrada e saída.

12. Como o jogo pede ao SO que imprima algo?

Usando uma convenção de serviço definida por nós, por exemplo uma chamada a uma rotina de saída. Ela usa a UART e retorna à aplicação.

13. Após desligar, o programa carregado continua na RAM?

Não há garantia de preservação. Nossa versão inicial precisará reenviar a aplicação; a imagem do SO permanece na EEPROM.

14. A CPU executa o SO e o jogo ao mesmo tempo?

Não na primeira versão. Uma sequência de instruções é executada por vez. A aplicação pode chamar serviços do SO e depois retornar a ele.

Meta: conseguir explicar em voz alta reset → busca em ROM → inicialização → cópia → salto → prompt → LOAD → RUN → retorno, indicando em qual memória está o código em cada etapa.
